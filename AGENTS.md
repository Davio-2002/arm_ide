# AGENTS.md

This file provides guidance to Codex (claude.ai/code) when working with code in this repository.

## What this is

A native mini IDE for AArch64 assembly: C++23, Dear ImGui (docking branch) on GLFW/OpenGL 3.3, the ImGuiColorTextEdit editor (goossens fork), real GNU cross tools for building, and QEMU for running and for the built-in step debugger (its GDB stub). Linux only (fork/exec, pipes).

## Commands

System packages: `binutils-aarch64-linux-gnu gcc-aarch64-linux-gnu qemu-user libglfw3-dev libfreetype-dev libvterm-dev`. ImGui (with its FreeType font loader, light hinting), the editor and nanosvg are pulled by CMake `FetchContent`, pinned to commit hashes in `CMakeLists.txt`, and so is the JetBrains Mono 2.304 release zip (SHA-256 checked). Binary assets (window icon, SVG icons, JetBrains Mono Medium — the one font for the UI and the code) are compiled in through `embed_as_bytes` in CMake (every `assets/icons/*.svg` is picked up by a glob as `<name>_svg.inc`, so a new icon only needs its `#include` in `icons.cpp`; the window icon and its sources live in `assets/app_icon/`), which writes `build/generated/*.inc` byte lists (no `#embed`: Ubuntu 24.04 has clang 18).

```bash
cmake --preset release            # configure (Ninja, clang++, Release, build/)
cmake --build --preset release    # build
./build/arm_ide examples/hello.s  # run; with no argument it reopens the most recent file
clang-format -i src/*.cpp src/*/*.cpp src/*/*.h
```

There is no test suite. Verify behaviour by running the app; logic in `core/` and `app/` can be exercised from a small standalone program linked against the `arm_ide_app` target (`build/libarm_ide_app.a`, which pulls in `arm_ide_core`; no window needed).

## Architecture

Three layers under `src/`, dependencies only point downward:

- `core/` — no ImGui/GLFW. `process` (spawn/poll/kill child processes, blocking `runCommand`), `toolchain` (`.s`: `as -g` + `ld`; `.c`: `gcc -g -O0 -static`; parses tool output into typed `Message`s with lines of the source only, reads the address→line table via `objdump --dwarf=decodedline --wide` with rows of other files and sequence ends as line 0, and symbol addresses via `nm`), `debugger` (runs the program under `qemu-aarch64 -g <unix socket>` and speaks the GDB remote protocol to it: registers `g`/`p`, memory `m`, breakpoints `Z0`/`z0`, `c`/`s`; QEMU does every system call, the program's output comes through the QEMU process pipe), `terminal` (the user's `$SHELL` on a pty from `forkpty`, its screen and scrollback kept by libvterm; keys go in as `TerminalInput`).
- `app/session` — the one `Session` class: open/save, build, run under QEMU, debug, breakpoints, register snapshots. It never draws; it exposes state as data (`console` of `Message`s with a `MessageKind`, `lineMarks` with a `LineMarkKind`, `pausedLine`, `lineToReveal`, `status`). Each folder is one CMake target: `core/` → `arm_ide_core`, `app/` → `arm_ide_app` (links `arm_ide_core`), `gui/`, `language/` + `main.cpp` → the `arm_ide` executable. The two libraries do not link ImGui, so GUI includes there fail to build.
- `language/` — the editor languages: `aarch64_words` (generated word lists), `aarch64_language` (the AArch64 syntax definition) and `c_language` (C with library names); built on `TextEditor`, so they compile into the executable.
- `gui/` — everything visible. The window frame: `window` (GLFW, fonts, zoom, settings file), `theme` (Islands Dark: every colour, ImGui style sizes, editor palette), `dialogs` (in-app modal popups: file browser for Open/Save As, discard-changes question), `menu` (shortcuts → `MenuActions` → `runActions` calling `Session`), `toolbar` (drawn inside the main menu bar and filling the same `MenuActions`: at the start an app badge and the current file's folder with a recent-files dropdown, at the end the file Build/Run use with an open-tabs dropdown and the Build/Run/Debug/Stop icon buttons), `statusbar` (bottom bar via `BeginViewportSideBar`: file breadcrumb, a dot and `session.status` for the program state, cursor line:column; drawn before `drawPanels` so the dockspace's work area excludes it), `icons` (SVGs from `assets/icons/` rasterized with nanosvg into OpenGL textures by `loadIcons`), `widgets` (shared header pieces: `iconButton`, `drawPillTab` — tabs rounded on all corners, with icon, × and unsaved dot — and `drawVerticalSeparator`).
- `gui/panels/` — one file per dock panel. `panels` (dock layout drawn as islands, the right tool strip, `drawPanels`, and the helpers every panel uses: `beginPanel`, `drawPanelTitle`, header button padding; every panel hides its dock tab bar and draws its own header row), `editor` (the code editor: one tab per open file — a `Document` with its own `TextEditor`, undo history and saved state — plus the gutter with breakpoints, line markers and autocomplete), `console` (Console/Build/Terminal tabs with debug and clear buttons, selectable and copyable output), `terminal_view` (the Terminal tab inside the Console: draws the libvterm cell grid and cursor, takes keys after a click, mouse selection copied with Ctrl+Shift+C or the right-click menu, Ctrl+Shift+V pastes, wheel scrolls back), `registers`, `memory`.

Data flow per frame (`main.cpp`): `session.update()` polls the QEMU process and, while debugging, waits up to 1 ms for a stop reply → `drawMenuBar` reads shortcuts, menus and toolbar into `MenuActions` → `drawPanels` (the Console's Resume/Step/Stop buttons add to the same `MenuActions`) syncs the editor from `Session` (read-only while debugging, markers rebuilt only when `lineMarksVersion` changes, cursor moved to `lineToReveal`) and draws → `runMenuActions` executes the collected actions once, unless a dialog is open.

Non-obvious points:

- The open files and their "modified" state (undo index) live in `gui/panels/editor.cpp`: the active tab is the file `Session` builds, runs and saves (`makeActive` sets `session.filePath`), and `drawLineDecoration`/`suggestCompletions` work on `drawingDocument`, the tab being rendered. Opening a file adds a tab (or selects its tab) and replaces an empty untitled one; closing a modified tab asks first, and quitting asks once for every unsaved tab (`whenChangesDiscarded`). The Editor panel hides its dock tab bar (`ImGuiDockNodeFlags_NoTabBar`) so the file tabs are its header. Session stores paths absolute and normalized, so one file never opens twice; `Session` only saves the text it is given. File actions that touch both are in `gui/menu.cpp` (`openDocument`, `saveDocument`).
- `Session` must have a fixed address: libvterm callbacks receive `&terminal` as user data, and the settings handler and gutter callback keep a `Session*`. It is a single static in `main.cpp`.
- Output: `buildLog` holds the assembler/linker output of the last build, `console` the program output and run results (cleared when a program starts). The Console panel switches to Build after a failed build and to Console after a good one (`buildCount`, `buildSucceeded`).
- Files: `filePath` is the file being edited, `programFilePath` the file last built; `lineMarks`, `lineToReveal` and `pausedLine` are lines of `programFilePath`, so the editor shows them only when it shows that file. `breakpoints` maps a path to its lines; Save As moves them to the new path, and the debugger gets the set of `programFilePath`.
- Breakpoint resume semantics: QEMU stops at once when continuing from a PC with a breakpoint, so `continueDebugger` first sends `s` (`continueAfterStep`) and then `c` unless it landed on another breakpoint; a fresh F8 uses `runDebugger` (plain `c`) so a breakpoint on the first instruction still hits.
- QEMU's user-mode GDB stub ignores the `0x03` interrupt byte while the program runs. To change breakpoints of a running program, `setBreakpointLines` sends SIGTRAP to the QEMU process (reported as `T05`; SIGINT would kill it), updates them and continues with `c`, which drops the signal.
- QEMU's single step (`s`) over an `svc` runs one more instruction after the system call, so `stepInstruction` steps an `svc` by running to a temporary breakpoint at PC+4 (lifting a breakpoint under the PC meanwhile; `restoreStepBreakpoints` undoes both at the next stop).
- Program input: the Console tab's input line sends a line (echoed into `console` like a terminal) to the program run by F5 or under the debugger; Ctrl+D in it sends end of file.
- F10 is a line step (`stepDebugger`): single steps until the PC is at the start of a line-table row of another line, or back at the row it started from (a loop on one line). In code without lines (glibc) it runs to the return address in `x30`; from glibc's `_start` it runs to `main` (`mainAddress`). For assembly every instruction is its own row, so it is one instruction. `pollDebugger` handles every stop reply that arrives within its timeout, so a line step is many round trips in one frame.
- Programs (F5 and debugger) run on a pseudo-terminal, not pipes (`startProcess`): stdin, stdout and stderr are its slave in canonical mode without echo or output translation. So glibc flushes `printf` at each line and before reading stdin, input arrives in lines, and `endProcessInput` writes the EOF character (Ctrl+D). Tools from `runCommand` still use a pipe and `/dev/null`.
- The editor picks the language per document from the extension (`setLanguage`): `.c`/`.h` get `cLanguage()` (`language/c_language`: the editor's built-in C plus C standard library names as identifiers, which it lacks), everything else AArch64; autocomplete uses the document's language words (case-insensitive and upper-case-following only for assembly), and `.` is a word character only in assembly.
- The Memory panel reads byte by byte; `Session::readMemory` fetches aligned 256-byte blocks over the stub and caches them until the next pause.
- Autocomplete is the editor's own popup (`SetAutoCompleteConfig`, Ctrl+Space or typing); `suggestCompletions` in `editor.cpp` only supplies words: the language's mnemonics, directives and registers plus identifiers in the document, prefix-matched ignoring case. `.` is a word character so `.glo` and `b.e` complete whole tokens.
- `aarch64_words.cpp` is generated data: every mnemonic, directive, `dc`/`ic`/`at`/`tlbi` operation and system register name that `aarch64-linux-gnu-as` (2.46, default `-march`, i.e. ARMv8-A + FP + AdvSIMD, no LSE/SVE/SME) accepts, found by assembling candidate names taken from `libopcodes`/`as` strings. Extension-only instructions are left out on purpose because the IDE's build would reject them.
- Set the editor palette at runtime (`setupEditor` applies `editorPalette()`). The `TextEditor` global's constructor copies a static palette from another translation unit, and static-init order made all colours transparent once.
- Dialogs are ImGui modals, not external programs: on GNOME Wayland a child process's window opens behind ours (no activation token), which looked like a freeze. They are asynchronous: `askForFileToOpen`/`askForFileToSave`/`askToDiscardChanges` take a callback that `drawDialogs` runs on a later frame, `whenChangesDiscarded` (menu) wraps the unsaved-changes check, and menu actions, dropped files and window close are ignored while `isDialogOpen()`.
- Settings (dock layout, zoom, recent files) are one ImGui ini at `$XDG_CONFIG_HOME/arm_ide/imgui.ini` (default `~/.config`), via a custom `ImGuiSettingsHandler` in `gui/window.cpp`. The default dock layout is built only when the dockspace ID `"MainDockSpace v3"` has no saved node; bump that string when adding a panel to the default layout.
- Islands: the dockspace lives in a transparent full-screen `##Ground` window padded by `islandGap`; dock title bars, splitters and empty nodes are made transparent while `DockSpace` runs (the splitter background uses `WindowBg`), and `beginPanel` hides a docked panel's own square background and draws its node as a rounded rect on the background draw list. Floating panels keep the normal background.
- Tools run with the source's folder as working directory (`runCommand`'s `directory`), and `buildProgram` makes the source path absolute first. `as -g` (binutils 2.46) segfaults when its working directory has been deleted, which happens when the IDE was started inside a `build/` that was later recreated.
- Building `foo.s` writes `foo.o` and `foo` next to the source; a source without an extension is rejected so the executable can't overwrite it.

## Code style

- clang-format with the repo `.clang-format` (LLVM base, 4-space indent, 100 columns, `InsertBraces`, spaces inside parentheses: `if ( x )`, `f( a, b )`, empty `f()`). Run it on every changed file.
- Every `if`/loop body in braces; no comments that restate the code.
- Keep it simple: free functions and plain structs, one `Session` class; no extra interfaces, wrappers or config for fixed values.
- New behaviour goes in the right layer: CPU/tool logic in `core/`, IDE behaviour in `Session`, drawing in `gui/`, colours in `gui/theme`. A new command is a `MenuActions` field (in `menu.h`), a shortcut in `readShortcuts`, a menu item in `drawMenus`, optionally a button in `drawToolbarEnd`, and a call in `runActions`.
- The owner prefers working step by step: propose a plan, implement one step, verify, then wait.
- The toolbar icons are JetBrains IntelliJ icons under Apache 2.0: keep `assets/icons/LICENSE.txt` and `NOTICE.md` next to them, and list any icon added there.
